## Root causes

### #2031 — readiness began before startup was ready to answer

Setup's post-handoff Chrome reload could reach a newly launched daemon before
authenticated health had established a stable serving state. A single early
probe was treated as the readiness fact, so a healthy daemon could time out
during its own startup boundary. Setup now owns readiness: it requires three
consecutive authenticated healthy reads before any dependent Chrome reload and
prints the number of attempts and consecutive successes.

### #2158/#2159 — maintenance modeled cleanup and foreground as best effort

The reload path knew that it had opened Chrome UI, but did not carry a complete
pre-operation UIA runtime-id set or process-qualified foreground lease through
every failure path. Cleanup could therefore lose the exact tab it owned, restore
a reused HWND or overwrite a human's later foreground choice. Separately, the
public success response discarded the detailed cleanup proof already produced
inside the installer, so callers could not distinguish a proven transaction
from an asserted one.

The replacement contract is one transaction. It records a bounded, unique
pre-operation tab baseline; the created maintenance tab/token; exact
HWND/PID/process-start/image identities; prior Chrome selection; replacement
host identity; exact cleanup; and the post-cleanup tab/foreground readback. A
superseding human foreground is preserved and reported, never overwritten.
Missing, stale, ambiguous, or partially cleaned state fails with a structured
`SYNAPSE_CHROME_MAINTENANCE_*` condition and repair guidance. The complete proof
is now typed into the public response and durable audit path.

### #2176 — the reload guard rejected the state that required reload

An extension with newly declared permissions is intentionally not yet the ready
replacement host: Chrome must reload it before those permissions become active.
The old readiness guard required a ready host before invoking that reload,
creating a circular precondition. Maintenance now classifies the installed
extension/profile state, invokes the exact existing-extension UI reload for the
pending-permission state, then proves the replacement build, worker digest,
active/granted permissions, cleanup, and foreground transaction. It does not
pretend the pre-reload host is ready and does not fall back to a second Chrome
profile or process.

### #2214 — an untrusted page controlled the privacy primitive

`pageScreenshot` inserted ordinary page-world `<div>` overlays before capture.
The captured page's CSS cascade therefore controlled the supposed masks. A
synthetic rule `div { opacity: .8 !important; ... }` made both known secrets
visibly readable in the stored PNG. The operation returned success and the file
SHA-256 was `e90…`, proving this was a real confidentiality failure rather than
a rendering hypothesis.

The page now contributes only geometry. The extension validates colors through
an extension-owned `OffscreenCanvas` using two sentinel assignments, pins the
same document ID through setup/scroll/cleanup, and returns exact rectangles and
RGBA values. Trusted Rust validates the complete manifest and overwrites the
stitched pixels after capture and background handling, before downscale,
encoding, and publication. Any unresolved, fractional/outside-only,
over-capacity, document-changed, cleanup-incomplete, or write-count mismatch
fails closed. Public evidence reports requested/resolved/applied/partial counts,
written pixels, document identity/hash, a privacy-safe commitment, and the
trusted backend; it contains no selector or secret text.

  including the fact that transitions outrank important declarations;

  used for isolated CSS-color parsing rather than page-world styling;
- [DICOM PS3.15 E.3](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/sect_E.3.html),
  which requires removal from stored pixel data rather than a display overlay;
- [Playwright's upstream screenshotter](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/screenshotter.ts),
  reviewed for capture lifecycle and restoration practice;
- [Microsoft `SetForegroundWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)
  and [foreground activation rules](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#foreground-and-background-windows),
  used to bound foreground ownership and restoration;
- [Chrome extension permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)
  and [extension service-worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle),
  used to separate declared, granted, active, and replacement-worker state.

The resulting design keeps the privacy write in trusted memory, makes page CSS
irrelevant, qualifies every UI identity, and treats Chrome's durable profile as
the permission Source of Truth.
